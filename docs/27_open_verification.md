# 未確認事項リスト — 検証と妥当性確認 (Open V&V Items)

## 目的

**まだ確かめていないこと**を 1 か所で管理する。
これまでは docs/24 の各節の「未実施」や README の注記に散らばっていて、
何が残っているかを一覧できなかった（2026-11-04 オーナー指摘）。

未確認には性質の違う 2 種類があるので、分けて管理する（定義は [24 冒頭](24_vv_plan.md)）。

| | 検証 (Verification) — §1 | 妥当性確認 (Validation) — §2 |
|---|---|---|
| 問い | **要求どおりに作れているか** | **作ったものが実際の作業に役立つか** |
| 基準 | 要求（SYS-F / SYS-NF）の受入基準 | 利用シナリオ（[20 §3](20_user_needs.md) US-xx）とニーズ（UN-xx） |
| やり方 | 単体・プロパティ・E2E・実機計測。手順どおりにやれば誰がやっても同じ結果 | **オーナーが実機で実際の作業として**シナリオを通し、問いに答える。自動化できない |
| 未確認の理由 | 治具・環境・権限・リリースが無い | **実作業で使った記録が無い**。検証が全部 PASS でも残る |
| 「いいえ」が出たら | 欠陥。修正して再確認 | 新しいニーズとして [20](20_user_needs.md) に足し、要求へ変換する（[24 §8](24_vv_plan.md)。場当たり修正で済ませない） |

- 本書に載っていない項目は「確認済み」か「未着手の機能」のどちらか、という状態を保つ。
- 「確かめる手段がまだ無い」ものも載せる（治具待ち・リリース待ちなど）。

## スコープ

| 含む | 含まない |
|------|----------|
| 実装済みだが実機・実環境で未確認の挙動（§1） | 未実装の機能（→ [06_roadmap.md](06_roadmap.md)） |
| README・ガイドなど利用者向けの記述のうち、未確認の主張（§1） | 要求と検証の対応の抜け（→ [23_traceability.md §4 GAP](23_traceability.md)） |
| 計画した試験のうち未実施のもの（docs/24 からの転記、§1） | 既知の制約・設計上の割り切り（→ 各要求の注記・ADR） |
| 利用シナリオを実作業として通していないもの（§2） | |

## 運用

1. **起票**: 未確認のまま実装・記述を入れるときは、同じ変更でここに 1 行足す
   （コミット前に。「後で書く」はしない）。利用者の作業の仕方を変える機能を入れたら、
   §2 にも 1 行足す（検証が通っても、役に立つかは別問題）。
2. **確認**: 実施したら §4「完了」へ移し、日付・結果・記録先を書く。
   - §1 で FAIL なら欠陥として扱い、修正の後に再確認する（完了には移さない）。
   - §2 は問いへの答えをそのまま書く（「はい」「いいえ ― 理由」）。「いいえ」は 20 に新しい UN を足してから完了に移す。
   §2 の記録の置き場所は本書とする（[24](24_vv_plan.md) TBD-V4 の決定）。
3. **リリース**: 「リリース前」が **必須** の項目が残っている間はタグを打たない。
   **β（`-beta.N`）では、§2 の妥当性確認（VA）と OV-7（Linux 実機）を免除**する（β は VA をするために出す。25 §1.1）
   （[25_release_strategy.md §4](25_release_strategy.md) のチェックリストの入力）。
   §2 の必須は [25 §3.3](25_release_strategy.md) Tier 2 の T2-6（妥当性確認）に当たる。
4. 元の文書（docs/24 など）の「未実施」の記述は残し、本書の ID を添える。正本は本書。

**現状: 記録された妥当性確認は 1 件も無い。** [24 §8](24_vv_plan.md) は「都度実施（記録なし）」で、
プロッタを含むすべてのシナリオについて、実作業で役立ったかを示す記録が存在しない。

- **プロッタ（VA-1〜3）を最優先**とする。表示の意味論（整列バケット、LIVE / Inspect / Paused、

## 3. プロッタの画面評価の所見（2026-11-04）

オーナーの依頼で、プロッタを**実際に動かして画面を見て**評価した。妥当性確認（§2）の代わりではなく、
オーナーが VA-1〜3 を行う前に、画面から分かる問題を先に洗い出すためのもの。

- **方法**: com0com（COM15→COM16）に、実機に近い信号を 100 Hz で流した。ノイズの乗った振動（accel ±0.3）、
  ゆっくり上がる温度（temp ≈ 24）、電流（current ≈ 1.2）に **1 サンプルだけのスパイク（6.0）を 7.3 秒ごと**、
  指定時刻に **1 回だけの外れ値（400）**、5 状態のステートマシン（0.4 秒だけの `FAULT_OVERTEMP_LATCHED` を含む）、
  120 ms ごとに切り替わる弁。UIA で操作し、スクリーンショットを見て判断した。
- **扱い**: 「欠陥」は直す前提で、直し方にオーナーの判断が要るもの。「所見」は妥当性確認（VA）でオーナーが判断する材料。

| **PF-4** | 所見 | **State Timeline は窓が長いと読めない。** 300 秒の窓では状態の色が細かく並ぶだけで、120 ms の弁は 2 色が混ざった 1 色に見える。10 秒の窓でも、0.4 秒だけの `FAULT_OVERTEMP_LATCHED` は「F…」としか出ず、色だけで見分けることになる | UN-06 → **VA-3** | まれで短い異常状態ほど見落としやすい表示になっている | 異常系の状態を目立たせる・短くても潰さない、などが要るかを VA-3 で判断 | 色の衝突は欠陥として**解消（2026-11-04、SYS-F-714）**: 意味のある色、登場順のパレット、異常は最低 4 px。長い窓での読みやすさ（トグルの表現・ホバー等）は VA-3 へ |
| **PF-5** | 所見（軽微） | **手動で再接続すると、プロッタのデータは新しくなるが、時間軸と「Duration」はプロッタを開いた時点から数え続ける。** 新しいデータは 18 秒分なのに「Duration: 2m 29s」と出て、300 秒の窓では左側が空白になった | SYS-F-802 / 803 | 時刻はプロッタのスレッド開始からの相対値 | Duration を「表示中のデータの長さ」にするか、セッションの切り替えで時間の原点を戻すか | **解消（2026-11-04）**: 新しいセッションごとに時間軸を 0 から、Duration はセッション開始からの最後のサンプル時刻、データが窓に満たない間は `[0, W]` で負の時刻を描かない。世代番号で画面に切り替わりを伝える（SYS-F-808、Fable の設計） |
| **PF-6** | **欠陥** | **LIVE の窓の右端が実時刻より先へ進み続ける。** 100 Hz で 160 秒後に 3 秒、187 秒後に 3.5 秒、データの右端が窓の右端より手前で止まった。10 秒の窓では約 10 分でデータが画面から消える計算 | US-01 / UN-01、VA-1（10 分以上眺める）に直撃 | 画面側は右端を実時間ぶん進め、取得時は `Math.ceil(右端)` を送る。バックエンドは送られた値を `end_ms` として返し、画面は「返った値が右端より先なら合わせる」ので、毎回の切り上げの端数が積もって戻らなかった（2026-11-04 の段階化の確認中に発見。前からある欠陥） | 右端を合わせるのは初回（範囲を指定しない要求）の応答だけにする | **解消（2026-11-04）**。再現テスト `does not let the live right edge creep ahead of wall time` を追加（修正前は失敗）。アプリで 100 Hz・3 分後もデータが右端まで届くことを確認 |
| **PF-7** | **欠陥** | **Disconnect → Clear → Connect で、旧セッションのチャンネルがプロッタに残り、新しいデータと混ざる。** ポートを閉じた状態の Clear でストアが無くなり、次の Connect が「初回の接続」扱いになって、プロッタが空にされなかった | SYS-F-802 / 806 | PF-5 の相談で Fable が発見（コードの読解） | ストアが外れた時点でプロッタを空にし、以後の接続を新しいセッションとして扱う | **解消（2026-11-04）**。`test_detach_clears_the_plot` |
| **PF-8** | **欠陥** | **データを受信した後でプロッタを開くと、それまでのデータが時刻 0 の 1 点に潰れる。** 10 行が 1 点、500 行も 1 点になった。並列テストで `test_batch_timestamps_are_spread` がまれに落ちていたのも同じ原因 | SYS-F-808 | プロッタの時刻の原点が「プロッタがストアに接続した時点」で、溜まっていた行をすべて経過 0 ms で読み、1 ms ずつ過去へ広げる処理が 0 で止まっていた。テスト 2 件で決定的に再現 | 原点をストアの作成時刻にし、溜まっていた行はストアの受信時刻の記録（約 100 ms ごと）で切って、その時刻に置く。記録が時計と合わない時（壁時計の補正）は今の時刻に戻す（Fable レビュー済み） | **修正済**（2026-11-04、実アプリで 10 秒分を後から開いて確認） |
