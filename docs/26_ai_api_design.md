# AI 向け API 設計 — トークン効率の Insight Bridge (v2)

## 目的

12 Mbps 級（1.5 MB/s）の受信中でも、**AI エージェントのトークン消費がデバイスの
スループットに比例しない** API を定義する。

現状の問題は帯域ではない（[25 §5.8](25_release_strategy.md) / ループバック TCP は
GB/s 出るので 1.5 MB/s は利用率 0.1%）。問題は **AI が読める量**である:

- 1.5 MB/s のテキストは毎秒 **約 37 万トークン**相当。どの LLM も消費できない。
- `serial_read_tail` の 1 MiB 上限は 1 回で **約 25 万トークン**。実質使えない。
- 特に `hex_dump` は 16 バイトあたり約 79 文字を出すため、`looks_like_text` が
  false になった瞬間、既定の 4096 バイト要求が **約 20 KB（6〜8k トークン）**を返す。

## 統括原則

> **アプリは「問い」に答える。干し草の山を送りつけない。**

AI 向けの応答は常に「**検証可能なハンドル付きの導出された事実**」であり、
生バイトはエージェントが**自分で辿り着いた 1 点の座標で意図的に買う**ものとする。

全ツールが従う 5 原則:

1. **バイト/呼び出しではなく、洞察/トークン。** 応答サイズは**文字数予算**で上限を
   持ち、到着データ量に依存しない。
2. **見栄えより正確さ。** 件数は正確な整数か、明示的に `est` を付ける。丸めない。
   **稀な事象を隠す要約は、要約しないより悪い。**
3. **ペイロードではなくハンドル。** バイトオフセット・テンプレート ID・カーソル
   （各 8 トークン程度）を返し、必要な箇所だけを 1 回だけ買わせる。
4. **時計は 1 つ、アドレス空間は 1 つ。** 唯一の真のアドレスは**ストリーム絶対
   バイトオフセット**。時刻は `DataStore::get_timestamp_for_offset`（実 epoch ms）
   のみ。行番号は参考値で、必ずオフセットを併記する。
5. **省略による嘘をつかない。** 切り詰め・サンプリング・索引遅延・ギャップ・世代
   リセット・テンプレート表の追い出しは、**予算に押し出されない固定枠**で必ず報告する。

**`max_tokens` ではなく `max_chars` を採る理由**: サーバはクライアントのトークナイザを
知り得ず、hex や CJK では推定が必ず外れる。全ツールは**レンダリング後の UTF-8 文字数**で
厳密に予算を課す（ログ的 ASCII では約 3.6 文字/トークンと説明文に明記する）。

## 1. 既存機構を「正」として流用してはいけない理由（コードで検証済み）

当初は「プロッタの集約器・パーサ・行インデックスを再利用すれば安上がり」と考えたが、
**いずれも AI 向けの正としては使えない**ことがコード上で確認された。

| 流用候補 | 使えない理由（本リポジトリで検証） |
|---|---|
| `PlotterState.aggregator` をチャンネル統計に | **GUI ライフサイクルに縛られている**。プロッタ窓の `Destroyed` で `set_enabled(false)`（`lib.rs:59`）、`start_plotter_thread` で `aggregator.clear()`（`lib.rs:243`）。人間がプロット窓を閉じるとエージェントのデータが消え、開き直すと過去の回答が遡って変わる |
| `PlotterThread` のタイムスタンプ | `timestamp_ms = start_time.elapsed()`（`thread.rs:157,181`）で **epoch ではない**。さらに `spread_batch_timestamps`（`thread.rs:62`）で再配分され、高レートでは多数行が同一 ms に潰れる。`serial::DataStore` 側に単調性を保証した実 epoch 索引が既にある（`serial/data_store.rs:383-437`） |
| `PlotterParser` を汎用ログの項目抽出に | セパレータ推定が空白まで落ちる。ラベルなしトークンは位置で `ch{i}` になり、非数値は全て `ChannelValue::State` になる。自由形式ログから**それらしいゴミのチャンネル**が生成され、動的キーでチャンネル配列が無制限に増える |
| `DataStore::total_lines()` / `get_line_offsets` をアドレス体系に | `record_line_offsets`（`serial/worker_thread.rs:29`）は **LF のみ**を記録し、`line_index` は `vec![0]` で初期化（`serial/data_store.rs:98`）されるため**空でも 1 行**と報告する。CR 単独終端のデバイスでは永遠に 1 行。**参考値としてのみ**使う |

**帰結**: AI 向けインデックスは**ブリッジが所有する独立モジュール**として新設する。

## 2. アーキテクチャ

### 2.1 新規モジュール

```
src-tauri/src/insight/
  mod.rs      // InsightIndex, IndexHandle, Snapshot
  mask.rs     // 純粋: 行 -> マスク済みテンプレート + スロット値（重点的に単体/プロパティ試験）
  index.rs    // テンプレート表・リング・重大度・チャンネル
  thread.rs   // DataStore を読む唯一の追加リーダ
  window.rs   // 純粋: ウィンドウ指定の解決、カーソルの生成/解釈
  find.rs     // DataStore 上のストリーミング正規表現走査（索引非依存）
  binary.rs   // 行指向でないストリームのフレーム要約
  render.rs   // 純粋: セクション組み立て + max_chars 予算 + フッタ
```

### 2.2 所有とライフサイクル（設計の要）

```rust
pub struct BridgeState {
    // ...既存...
    pub index: Arc<InsightIndex>,            // BridgeState::new() で常時生成
    index_thread: Mutex<Option<IndexThread>>,
}
pub struct BridgeCtx {
    // ...既存...
    pub index: Arc<InsightIndex>,            // 追加
}
```

- インデックスは**ブリッジの所有物**であり、プロッタ窓やメイン窓の開閉に影響されない。
- `IndexThread` は `bridge_set(enabled=true)`（`bridge.rs:989` 付近）で開始し、
  `false` で停止する。**AI Bridge は既定 OFF** なので、使わない利用者は CPU/メモリを
  一切払わない。
- スレッド構造は実績のある `PlotterThread::run` に倣う（毎回ストアを再解決、
  `Arc::ptr_eq` で世代差し替え検知、1 MiB で読み出し上限、読み取り失敗が続いたら
  スキップアヘッド）。ただし**スキップは必ず `gap` として明示記録し、隠さない**。
- `--mcp` は別プロセス（`lib.rs:30`）で TCP しか持たないため、**ロジックは全て
  ブリッジ側**に置き、MCP アダプタは渡された `text` を出すだけの薄い描画器とする。

### 2.3 応答エンベロープ（新メソッド共通）

```json
{
  "text":   "…レンダリング済み・予算内の本文…",
  "data":   { /* GUI や非 LLM クライアント向けの構造化等価物 */ },
  "meta":   { "gen":3, "mode":"text", "exact":true, "coverage_pct":100,
              "index_lag_bytes":0, "sampled":null, "gaps":0 },
  "budget": { "max_chars":1800, "used_chars":1642, "truncated":true,
              "next":"serial_patterns(window=\"60s\", limit=41)" }
}
```

MCP ツールは `text` をそのまま返す。予算の適用は `insight::render` の**1 箇所のみ**で行う。

## 3. 時刻・ハンドル・世代・カーソル

### 3.1 唯一の時計

`timestamp_index` は `UiNotifier` が 100 ms ごと（バイトが増えたときのみ）に追記し、
NTP のステップに対して単調性が保証されている（`serial/data_store.rs:383-414`）。したがって:

- 壁時計値は必ず **±100ms** を併記する。
- `window="30s"` は**バイト範囲に解決**し、その範囲を応答に明記する
  （`window=30s → off 128,204,001..132,412,000 (±100ms)`）。エージェントが再導出できる。
- `timestamp_index` が空なら、時刻指定ウィンドウは
  `no timing data yet; use window="all" or an offset window` で**失敗させる**。
  時刻を捏造しない。

### 3.2 ハンドルと世代

| ハンドル | 形式 | 保証 |
|---|---|---|
| バイトオフセット | `@off=12873456` | **正**。`serial_read_range` にそのまま使える |
| テンプレート ID | `t88` | セッション内で安定 |
| カーソル | `v1:g3:o…:l…:e…` | **世代 `g` を内包** |

世代（`gen`）は Clear / ポート再オープン / 巻き戻りで増える。**古い世代のカーソルは
エラーにせず**、`gen` が変わった事実と新しい開始位置を明示して返す（購読側が
静かに嘘のデルタを受け取らないため）。

## 4. ツール一覧（新規 6 / 既存 7 は維持）

機能は**パラメータに畳む**（差分専用ツールではなく `compare_to`、タイムライン専用
ツールではなく `buckets`）。MCP スキーマの常駐コストを約 1.0k トークンに抑える。

| ツール | 目的 | 代表コスト | 実装の要 |
|---|---|---|---|
| **`serial_digest`** | 1 コールで全体を把握（「とりあえず tail して眺める」を置換） | 約 500 tok（1800 字上限） | `InsightIndex::snapshot()`。**`get_data` を 1 回も呼ばない** |
| **`serial_watch`** | カーソル以降の**集約された変化のみ**。コストがスループットに非依存 | 約 180 tok（4 KB でも 40 MB でも同じ） | テンプレート別デルタ + サーバ側ロングポール |
| **`serial_find`** | サーバ側で正規表現検索し、**件数**を返す | 約 350 tok（`count_only` なら約 60） | `regex::bytes` で 256 KiB 窓・4096 B 重なりのストリーミング走査。**索引不要** |
| **`serial_patterns`** | テンプレート・ヒストグラム（最高の洞察/トークン）。`id=` で詳細、`compare_to=` で差分 | 約 180〜620 tok | テンプレート表 + スロット統計 |
| **`serial_sample`** | 生行が本当に要るときの**代表・重複畳み込み・上限付き**の抜き取り | 約 380 tok（n=20） | `tail｜head｜stratified｜around_offset｜by_template` |
| **`serial_channels`** | 数値/状態テレメトリ（**独自**抽出器。プロッタのパーサは使わない） | 約 300 tok | ラベル付き項目のみを対象にした保守的な抽出 |

### 代表例: `serial_watch`（最重要）

```
watch gen=3 · +2.10 MB · +71,204 lines · 4.31 s · 1.42 MB/s
ALARM +0 err · +3 warn (exact)
NEW   t94 "W: rx overflow q=<N:64..64>" x3  first @off=134,110,221
DELTA t1 +68,900 · t7 +2,290 · t12 +11 · other +0
CHAN  temp mean 23.4 (was 23.3) min 21.9@off=134,002,111 max 25.9@off=134,510,900
cursor v1:g3:o134612044:l4286084:e1756900000
— nothing withheld
```

0.5 Hz で追随して **約 360 tok/分**。生ストリーム換算 2,250 万 tok/分に対して
**約 6 万分の 1**。

## 5. 既存ツールの扱い（何も削除しない）

| ツール | 扱い | 変更点 |
|---|---|---|
| `serial_status` | **出力のみ変更** | 末尾の `raw: {全 JSON}` を廃止（情報ゼロでコスト倍）。`gen` / 索引状況 / レートを追加 |
| `serial_ports` | 維持 | — |
| `serial_read_tail` | **出力を有界化** | `max_chars`（既定 4000）、`collapse_repeats`、`format`(`auto｜text｜hex｜lines`) を追加。`bytes` 既定 4096 は互換のため据置 |
| `serial_read_range` | **出力を有界化** | 同上。バイト厳密な意味論は不変 |
| `serial_send` / `serial_send_hex` | **加算的変更（実装済）** | `expect`（正規表現）/ `expect_timeout_ms` を追加。`reply_chars` は入れていない（返信の文脈量は `wait_for` の固定枠で足り、パラメータを増やす価値が無かった）。`expect` を渡さなければ挙動は完全に同一 |
| `serial_wait_for` | **スキーマ維持 / 実装を刷新（実装済）** | 走査を**ブリッジ側**へ移した（下記の実バグ修正を兼ねる） |
| ブリッジ `subscribe` | 維持 | GUI・非 LLM 用。**MCP ツールとしては公開しない**（256 KiB/50ms の base64 は LLM に不適） |

`PROTOCOL_VERSION` を 1 → 2 に上げる。新パラメータを送らない v1 クライアントは挙動不変。

### 5.1 発見された実バグ: `serial_wait_for` の読み負け

現行のクライアント側ポーリングは `WAIT_WINDOW_BYTES=65536` を `WAIT_POLL_MS=500`
ごとに読む（`mcp_stdio.rs:38-42`）＝**実効 131 KB/s の走査**。12 Mbps（1.5 MB/s）では
**約 11 倍の読み負け**となり、ポーリング間に約 750 KB 到着するのに末尾 64 KB しか
見えない。結果 `chunk_offset > cursor` がほぼ毎回成立して**累積バッファが置換**され
（gap 扱い）、デバイスの返信はポーリングが着弾の約 43 ms 以内に落ちたときしか
観測できない。

**暫定修正（適用済み。2026-09-04）**: 窓を固定値から**適応的**に変えた。要求量を
`前回判明した未読分 + 64 KiB`（`MAX_READ_LENGTH` = 1 MiB で頭打ち）とすることで、
到着レートに応じて窓が自動的に広がり、**約 16 Mbps まで読み負けが起きない**。
ただし窓を広げると蓄積が毎秒 MB 単位で伸びるため、走査済みの接頭辞を解放して
`WAIT_RETAIN_BYTES`(64 KiB) の重なりだけ残す。`acc_start` を同量進めるので
オフセットは絶対値のまま狂わず、`bytes_scanned` は累計を保つよう別管理にした。
Rust 版・Node 参照版の両方に適用（DEBT-6 の同期義務）。

そのときに残った限界（当時の **DEBT-8**）: 単一マッチが 64 KiB を超えると切り出し
境界で取り逃がし得る。また 16 Mbps を超えると再び読み負ける。ポーリングと base64
往復という構造自体は変わっていない。

→ **恒久対策（実装済。2026-09-07 / §7.5）**: 待機をブリッジ側へ移した。送信前の
`total_bytes` から サーバ側で前方走査するので、窓・蓄積・base64 往復のすべてが不要になり、
`gap: true` という失敗モードと上記の限界が構造的に消えた。

## 6. 誤誘導防止（規範。これは助言ではなく受入基準）

### 6.1 セクション優先順位（予算はこの順に埋める）

```rust
enum Section { Header, IndexHealth, Alarm, NewTemplates, Rare, Top, Channels, Timeline, Samples }
// フッタは 120 字を先に確保し、決して落とさない
```

予算が逼迫したときに削るのは**サンプル数**であって、**アラームは決して削らない**。
実行時ヒューリスティックではなくコンパイル時の順序で保証する。

### 6.2 規則

1. **正確な件数のみ。** 丸めない。不正確な値は `est` を前置し、理由（`sampled 1/8`）を併記。
2. **稀少イベントの床。** top-N を出す前に、ウィンドウ内で `count <= 5` のテンプレートと
   ウィンドウ内で初出のテンプレートを、正確な件数と初出/最終オフセット付きで
   `RARE` / `NEW` に必ず列挙する。**400 万分の 1 の行は、支配的な行より優先して出る。**
   `RARE` すら上限に当たる場合は `RARE 12 of 47 shown` と明示し、全件を出す呼び出しを
   フッタに書く。黙って短くしない。
3. **重大度は常に全バイトを正確に走査。** `error｜fail｜fatal｜panic｜timeout｜overflow｜warn`
   等の `memchr` ベースの大小文字無視走査を**取り込む全バイト**に対して行う
   （マスク処理より約 10 倍安い）。したがって `coverage_pct == 100` である限り
   `ALARM` 件数はテンプレートのサンプリングと無関係に正確。
4. **極値には必ずハンドルを付ける。** すべての `min`/`max`/`peak`/`first`/`last` に
   発生バイトオフセットを併記する。「要約が致命的事象を隠した」を、
   `serial_read_range` 1 回で検証可能な状態に変える。
5. **カバレッジを常に明示し、裸のゼロを禁じる。** `err=0` 単独は**不正な出力**。
   合法なのは `err=0 (exact, coverage 100%)` か
   `err=0 (coverage 62%, indexing 82.1 MB behind)` のみ。
6. **ダウンサンプルはスパイクを構造的に保存する。** バケットは平均だけでなく
   min/max とその発生オフセットを保持する（GUI プロッタの INV-7 / min-max バンドと
   同じ思想。[22 ADR-06](22_architecture_description.md) と整合）。

### 7.1 段階 0 の実装記録（2026-09-05）

設計と 1 点だけ変えた。**「後段適用」ではなく、描画前にバイト単位で切り出す**。
文字列を切ると出したバイト範囲を絶対オフセットで言えず、原則 3「ペイロードでは
なくハンドル」が満たせないため。hex は 1 行 = 16 バイト = 79 文字と固定なので
文字数からバイト数を厳密に逆算でき、テキストは lossy UTF-8 の文字数を
`Utf8Error::error_len()` の規則どおり数えて逆算する（`head_bytes_within_char_budget`）。
CJK ログを「1 バイト = 1 文字」で概算すると予算の 1/3 しか使えないため、
バイトではなく**文字を数える**ことに意味がある。

決定事項:

- **切り詰める側**: `serial_read_tail` は末尾（「最新」が欲しい呼び出し）、
  `serial_read_range` は先頭（「この位置から」が欲しい呼び出し）を残す。
- **フッタは落とさない**。溢れたら本文だけを削る。落とした範囲は前後どちらにも
  出るので（`lines` は両端）、**両方**を `serial_read_range(...)` 呼び出しとして
  正確に示す。
- `max_chars` の下限を 500 とした。ヘッダ+フッタ用の確保が 240 文字あり、
  封筒すら入らない予算を許すと本文が空でも上限を超えるため
  （プロパティ試験が実際にこの溢れを検出した）。
- `collapse_repeats` はバイト予算の**後**に効く。反復の多いログでは `bytes` も
  併せて上げる必要がある旨をツール説明文に明記した。

実測: `serial_status` は 4 行のみ（同内容の `raw: {全 JSON}` を廃止）。
4096 バイトのバイナリ = **20,223 → 3,902 文字**。受入基準
「どんな入力・書式・予算でも文字数が `max_chars` を超えない」は
Rust 側でプロパティ試験、Node 側で smoke に固定した。

### 7.2 段階 1 の実装記録（2026-09-05）

`src-tauri/src/insight/` を新設し、走査ロジックを `find.rs` に純粋関数として
置いた。実ストアに依存しないよう `ByteSource` トレイト（`total_bytes` /
`read`）を挟み、試験は `Vec<u8>` 裏の実装で**欠落と時間切れを再現**する。
DEBT-7 が指摘した「IO ループから純関数を抽出して細粒度検証する」方向を、
新規コードで最初から守っている。

走査の正確性で押さえた点:

- 256 KiB 窓 + 4096 B 重なり。**窓の末尾で終わるマッチはその窓では採らない**
  （打ち切られている可能性があるため）。次の窓が重なりごと読み直して完全な形で
  拾う。重複計上は「報告済みオフセット」で抑える。窓境界ちょうどに置いた
  マッチが 1 回だけ数えられることを試験で固定した。
- `bytes_scanned` は重なりの二重読みを差し引いた実効値。カバレッジ率が
  100% を超えないため。
- 欠落（DEBT-5 で `get_data` が Err を返す領域）は窓ごと飛ばし、
  `gap_bytes` に積む。**飛ばしたら `exact` は必ず false**。
- 3 秒で打ち切り、`complete=false` を返す。クライアント側の 5 秒
  タイムアウトで無言で失敗させ「見つからなかった」と誤解させないため。
  打ち切り時は再開用の `from=` を必ず添える。

出力の規範（受入基準として試験に固定）:

- 件数は `exact` か `AT LEAST — <理由>` のどちらかで、**丸めない**。
- **裸のゼロを出さない**。`matches: 0` には必ず走査バイト数・カバレッジ率・
  欠落・所要時間が付く。「見つからなかった」と「見に行けなかった」を
  混同させない。
- ヒットを打ち切ったら `showing N of M hits` と明示し、`serial_read_range`
  で文脈を取る方法を添える。全件出せたときだけ `all hits listed.`。

返答に `base64` が混ざらないこと、応答サイズがキャプチャ長に依らないことを
ブリッジ側の試験で固定した（`find` の存在意義そのもの）。ツール数は 7 → 8。
`tools/list` のスキーマ常駐コストが 9000 文字を超えないことも試験で押さえた。

### 7.3 段階 2 の実装記録（2026-09-07）

`src-tauri/src/insight/` に `mask.rs` / `window.rs` / `index.rs` / `render.rs` /
`thread.rs` を追加し、ブリッジに `digest` / `watch`、MCP に `serial_digest` /
`serial_watch` を足した。`PROTOCOL_VERSION` は 1 → 2。

実測（2 万行を索引した状態）: **digest 901 文字（約 250 トークン）**、
**watch 394 文字（約 110 トークン）**。3,042 行でも 20,000 行でも digest の
文字数は同じ桁に収まることを試験で固定した（`test_digest_size_does_not_grow_with_the_capture`）。

設計から変えた点と、その理由:

- **テンプレート表の追い出しは LRU（最後に見た位置が最も古いもの）**。当初
  「稀なものから追い出す」を検討したが、それは §6.2-2「稀少イベントの床」と
  真っ向から矛盾する。支配的な行は常に直近なので生き残り、落ちるのは
  「古くて以後現れないもの」になる。追い出した数と行数は `evicted` として
  必ず報告するので、TOP の合計と総行数が黙って食い違うことはない。
- **差分では first / min / max を出さない**。テンプレート統計は全期間のもので、
  窓での増分（`+3`）の隣に全期間の極値を並べると「この窓で 21.9〜25.9 だった」
  と読めてしまう。窓の外を指しうる値は書かない。初出テンプレートだけは
  全期間 = その窓なので例外として出す。
- **写しとカーソルは同じロックで取る**（`snapshot_with_checkpoint`）。別々に
  取ると、間に取り込まれた行がどちらの応答にも載らないか、次の `watch` が
  「基準点が無い」と言い出す。
- **`watch` のロングポールは 3000ms 上限**。MCP クライアントの 1 リクエスト
  タイムアウトが 5000ms なので、それより手前で必ず返す。設計が想定していた
  無制限のロングポールは、クライアント側のタイムアウト設計と衝突する。
- **時系列バケットは素材の範囲を明記する**。チェックポイント環は有界
  （96 個・1 秒間隔）なので、長い窓では前半に素材が無い。それを黙って 0 と
  して出すと「その時間帯は静かだった」という嘘になるため、
  `from N checkpoint(s) covering off A..B` を必ず添える。
- **行の切り出しは LF と CR の両方**。`DataStore::record_line_offsets` は LF の
  みを見る（§1）ので、CR 終端デバイスでは行数が永遠に 1 になる。索引は自前で
  両方を行区切りとして扱う。
- **重大度は出現回数**（1 行に 2 回あれば 2）。行単位に丸めると「1 行に
  エラーが 3 件」を隠すことになる。チャンク境界で語が割れても取り逃がさない
  よう 7 バイトの持ち越しで再走査し、二重計上しないことをプロパティ試験で固定した。
- **`Section::Channels` は席だけ用意した**。中身は段階 5。優先順位は
  列挙順そのものなので、後から挿すより先に席を決めておく方が安全。

達成できなかった目標:

- **MCP スキーマの常駐コスト**。設計は「約 1.0k トークン」を掲げていたが、
  digest / watch を足して 7.1k → **9.0k 文字（約 2.5k トークン）**になった。
  そもそも既存 8 ツールの時点で約 1.9k トークンあり、目標は最初から達成できて
  いなかった。1 回の `tail` が 25 万トークンだったことに対する取引としては
  妥当だが、これ以上は**説明文を削るのではなくツールを増やさない**ことで守る
  （試験の上限を 10,000 文字に置いた）。
- **12 Mbps での索引の追随性能は未実測**（§9 のまま）。単体では
  `IndexThread` が 1 MiB ずつ読んで追随することしか確認していない。

### 7.4 段階 3 の実装記録（2026-09-07）

`insight/sample.rs`（純粋）を追加し、ブリッジに `sample`、MCP に `serial_sample` を
足した。テンプレート詳細は **`serial_digest(template="t12")`** として畳んだ。

**`serial_patterns` を別ツールにしなかった理由**: 設計の §4 は 6 ツールを新設する
想定だったが、実装してみると `serial_patterns` の中身は 3 つに分かれ、そのうち
2 つは既にある:

| `serial_patterns` の機能 | 実際の置き場所 |
|---|---|
| テンプレートのヒストグラム | `serial_digest(window=, top=)` がそのもの |
| `compare_to=` による差分 | `serial_watch(cursor=)` がそのもの（段階 2 で実装済み） |
| `id=` によるテンプレート詳細 | **新規**。`serial_digest(template=)` として畳んだ |

残る「詳細」だけのために 1 ツール増やすと、`tools/list` の常駐コストが
全リクエストに乗る。設計自身の原則「**機能はパラメータに畳む**」（§4 冒頭）に
従って `digest` のパラメータにした。結果、段階 3 で増えたツールは
`serial_sample` の 1 つだけで、常駐コストは 9.0k → 約 10.5k 文字に留まった。

`serial_sample` の設計判断:

- **端の欠けた行は捨てる**。読み出し窓の両端は行の途中でありうる。切れた行を
  1 行として見せると、エージェントはそれを実データだと信じる。捨てた結果 0 行に
  なったら、その理由と次の手（`n` を増やす / `serial_read_range`）を必ず出す。
- **索引はテンプレートごとに直近 4 件の「オフセットだけ」を覚える**（8 KB）。
  行本文を持つと 256 テンプレート分で数十 MB になる。`by_template` は
  必要になった時点で `DataStore` から読み直す。覚えているのが 4 件だけである
  ことは応答に明記する（`showing the last 4 occurrence(s) the index kept`）。
- **`stratified` は重なったら短くする**。範囲が狭いときに同じ位置を n 回
  読んで n 行あるように見せない。
- 重複畳み込み `[xN]` の N は**正確**。丸めない。

`digest(template=)` の詳細モードは、概要モードと違い**数百バイトだけ**
キャプチャを読む（索引が覚えたオフセットから実際の行を引くため）。概要モードが
`get_data` を 1 回も呼ばないことは試験で固定したままにしている。

### 7.5 段階 4 の実装記録（2026-09-07）

待機の**走査**をブリッジへ移した（`bridge::method_wait_for`）。クライアント側に
残ったのは「区切って呼び直し、間でキャンセルを見る」だけ。

消えた失敗モード（DEBT-8 の 3 点すべて）:

| 旧実装の制限 | 解消した理由 |
|---|---|
| 固定 64 KiB 窓 / 適応窓でも約 16 Mbps で読み負け | 窓が無い。ストアを `from` から現在の末尾まで**そのまま前方走査**する |
| `WAIT_RETAIN_BYTES`(64 KiB) を超える単一マッチを取り逃がす | 蓄積を持たない。残る制限は再開の重なり 4 KiB を超えるマッチのみ |
| base64 の往復 | ブリッジ内でストアを直接読む。ワイヤに乗るのはマッチ 1 件の情報だけ |

さらに、`send` が**書き込み直前の `total_bytes`** を返すようにした。
`serial_send(expect=...)` はそのオフセットから走査するので、
「返信が最初のポーリングより前に着弾すると観測できない」という §5.1 の競合が
**構造的に**消える（時間ではなく位置で決まるため）。Node 版のスモークに
`a reply that lands before the first scan is not missed` として固定した。

設計から変えた点:

- **1 リクエストで待ち切らない**。設計は「待機をブリッジ側へ移す」とだけ書いて
  いたが、MCP クライアントの 1 リクエストタイムアウトは 5000ms で、
  10 分待つ要求をそのまま 1 往復にはできない。加えて**ブロック中のソケット
  読み出しは中断できない**ので、`notifications/cancelled` に反応できなくなる。
  そこでサーバ側の 1 回の待機を [`WAIT_SERVER_MAX_MS`] = 1000ms で切り、
  クライアントが `next_from` で呼び直す形にした。キャンセル検知の遅延は
  最大 500ms → 最大 1000ms に**悪化する**が、そのぶん読み負けが消える。
- **重なりの計算はブリッジに 1 箇所だけ**置いた（`next_from`）。クライアントは
  それを渡し返すだけなので、Rust 版と Node 版で境界の扱いがずれない。
- **`match_text` をブリッジが返す**。Node 版は lossy 変換した文字列上で
  マッチしていたため、不正 UTF-8 が混じるとオフセットがずれていた
  （DEBT-6 の既知の非対称 (2)）。オフセットも一致文字列もブリッジが
  生バイトから決めるので、**この非対称も解消した**。

残る制限: 再開の重なり（4 KiB）を超える単一マッチは境界で取り逃がし得る。
64 KiB だった頃より狭いが、実用上そのような長さの単一マッチは無い。
必要なら `insight::find::SCAN_OVERLAP` を上げるだけで広がる。

### 7.6 段階 5 の部分実装と、残りをやらなかった理由（2026-09-07）

段階 5 のうち、**「バイナリ/自由形式で自信満々に嘘をつくのを止める」部分だけ**を
実装した。索引が取り込んだ制御バイトの割合を数え、行指向でなさそうなときは
`serial_digest` の固定枠（INDEX セクション）で明言する:

```
INDEX stream does not look line oriented (11.3% control bytes): the line counts and
      templates below are NOT meaningful. Use serial_find on byte patterns and
      serial_read_range(format="hex") instead
```

判定は「タブ / CR / LF / 表示可能 ASCII / 0x80 以上のいずれでもないバイト」が
5% を超えたら。0x80 以上を可とするのは **CJK ログをバイナリと誤認しないため**で、
この向きの誤検知の方が害が大きい（一様乱数のバイナリはこの定義で約 11% になるので、
5% は「テキストではまず起きず、バイナリなら確実に超える」線）。256 バイト未満では
判定しない。

**`serial_channels` は実装しなかった。** 段階 2〜3 を作った結果、この機能の中身は
既に別の形で存在している:

| `serial_channels` の意図 | 実際の置き場所 |
|---|---|
| ラベル付き数値項目の統計（mean/min/max） | `serial_digest(template="t1")` がテンプレートの全項目について min/max/last を**発生オフセット付き**で返す |
| 変化の追随 | `serial_watch` のテンプレート別デルタ |
| 状態値のタイムライン | `serial_digest(buckets=N)` |

テンプレート単位の統計は「ラベル推定」を必要としない分だけ**誤りにくい**
（設計 §1 が「プロッタのパーサは自由形式ログからそれらしいゴミのチャンネルを
作る」と退けたのと同じ理由が、独自の抽出器にもそのまま当てはまる）。
`tools/list` の常駐コストを払ってまで別ツールにする理由が見当たらなかったので、
**やらないことを選んだ**。必要になったら `digest(template=)` の出力を横に並べる
だけなので、後から足すのは容易。

**`binary.rs` のフレーム要約も未着手。** 「どこがフレーム境界か」はプロトコル依存で、
推定を外すと今度はフレーム単位で嘘をつく。上の警告で「テンプレートを信じるな」と
言えている以上、当てにならない推定を足すより、`serial_find`（バイト正規表現）と
`serial_read_range(format="hex")` に誘導する方が正直。実デバイスで必要になった
時点で、そのプロトコルを見てから設計するのが妥当と判断した。

## 8. 試験義務（本リポジトリの V&V 方針に整合）

- `mask.rs` / `window.rs` / `render.rs` は**純粋関数**として単体 + プロパティ試験
  （マスクの冪等性、予算超過が起き得ないこと、セクション優先順位の保存）。
  → これは [24 §6.1.1](24_vv_plan.md) のハーネス方針、および **DEBT-7**（IO ロジックを
  純関数へ抽出して細粒度検証する）と同じ方向であり、新規コードで最初からそれを守る。
- `find.rs` は窓の継ぎ目（4096 B 重なり）に跨るマッチのプロパティ試験。
- 索引スレッドは既存の状態遷移試験（`state_transition_tests.rs`）に
  Attach/Swap/Detach × 索引の 1-switch を追加。
- 誤誘導防止規則（§6）は**受入基準**として、稀少イベントが top-N に埋もれないこと、
  `err=0` が裸で出ないことをテストで固定する。

## 9. 受け入れたリスク（明示）

- テンプレート表は有界（追い出しあり）。追い出しは `evicted` として必ず報告する。
- 行指向でないストリームでは行数もテンプレートも意味を持たない。判定して
  固定枠で明言する（§7.6）が、**判定自体はヒューリスティック**であり、
  制御バイトの少ないバイナリ（例: 0x80 以上が支配的なフレーム）は見逃す。
- 索引は AI Bridge が ON のときだけ動く。OFF の利用者はコストゼロだが、
  ON にした直後は履歴の索引が無い（`coverage_pct` で明示）。
- 12 Mbps での索引スレッドの追随性能は**未実測**（現時点の実測は ~2 Mbps まで）。
  FT232H 級の治具が入手でき次第、[24 §6.5](24_vv_plan.md) の T2-5 に
  「AI Bridge ON のままキャプチャ欠落ゼロ + 索引が追随」を追加して測る。
