# Phase 7: シリアルプロッタ (Serial Plotter)

*   **目標:** Arduino IDEシリアルプロッタのようなリアルタイムグラフ描画機能に加え、Grafanaのステートタイムラインのような状態表示機能を実装する。

## 概要

### コンセプト

本プロッタは以下の2つの可視化モードを提供する：

| モード | 用途 | 参考 |
|--------|------|------|
| **ラインチャート (Line Chart)** | センサー値、アナログ入力等の連続データをリアルタイムでプロット | Arduino IDE Serial Plotter |
| **ステートタイムライン (State Timeline)** | 離散的な状態変化（ON/OFF、エラーコード等）を時系列で可視化 | Grafana State Timeline Panel |

### アーキテクチャ概要

```text
[受信スレッド]
     ↓ (Raw Bytes)
[メインデータストア (RingBuffer)]
     ↓ (通知/ポーリング)
[プロッタ解析スレッド (Backend)]  <-- ここで数値/状態にパース
     ↓ (Parsed Values)
[プロッタデータストア (Backend)]
     ↓ (Events / Commands)
[プロッタウィンドウ (Frontend)]   <-- 描画のみ担当
```

## データフォーマット仕様

### サポートするデータ形式

Arduino IDE互換の形式を基本とし、拡張形式もサポートする。

| 形式 | 説明 | 例 |
|------|------|-----|
| **単一値** | 1行に1つの数値 + 改行 | `123.45\r\n` |
| **複数値 (CSV)** | カンマ/タブ/スペース区切り | `10,20,30\r\n` または `10\t20\t30\r\n` |
| **ラベル付き値** | `label:value` 形式 | `temp:25.5,humidity:60\r\n` |
| **ヘッダー行** | 列名定義（初回のみ） | `temp,humidity,pressure\r\n` |
| **状態値** | 文字列/数値で状態を表現 | `state:RUNNING\r\n` または `motor:1\r\n` |

### 改行コード

以下の改行コードを自動認識する：

- `\r\n` (CRLF) - Windows / Arduino標準
- `\n` (LF) - Unix/Linux
- `\r` (CR) - 旧Mac

### データパース仕様

```rust
/// パースされた1行分のデータ
#[derive(Debug, Clone)]
pub struct ParsedDataPoint {
    /// 受信時刻（ミリ秒精度）
    pub timestamp_ms: u64,
    /// チャンネルデータ（ラベル → 値）
    pub channels: HashMap<String, ChannelValue>,
    /// チャンネル順序（CSV列順を保持）
    pub channel_order: Vec<String>,
}

/// チャンネル値（数値または状態）
#[derive(Debug, Clone)]
pub enum ChannelValue {
    /// 数値 (Line Chart用)
    Numeric(f64),
    /// 状態値 (State Timeline用)
    State(String),
}
```

### パースルール

1. **行区切り:** 改行コードで1データポイントを区切る
2. **値区切り:** カンマ `,` > タブ `\t` > スペース ` ` の優先順位で検出
3. **ラベル検出:** コロン `:` でラベルと値を分離
4. **型推論:**
   - 数値としてパース可能 → `ChannelValue::Numeric`
   - パース不可 → `ChannelValue::State`
5. **ラベル自動生成:** ラベルがない場合は `ch0`, `ch1`, ... を自動付与
6. **ヘッダー検出:** 最初の行がすべて非数値の場合、ヘッダーとして解釈

### エラーハンドリング

| ケース | 挙動 |
|--------|------|
| パース失敗行 | 該当行をスキップしてログに警告を出力 |
| 値の欠落 | 直前の値を継続（ホールド） |
| 異常な数値 (NaN, Inf) | 除外してプロットに含めない |

## ラインチャート (Line Chart)

### 基本機能

| 機能 | 説明 |
|------|------|
| **リアルタイム描画** | 受信データをリアルタイムでプロット（最大60fps） |
| **複数チャンネル** | 最大16チャンネルを同時表示 |
| **カラー自動割り当て** | 各チャンネルに異なる色を自動割り当て |
| **凡例 (Legend)** | チャンネル名と現在値をツールチップ/パネルで表示 |
| **時間軸スクロール** | X軸は時間を表し、新データで自動スクロール |

### 軸設定

| 項目 | 説明 | デフォルト |
|------|------|-----------|
| **X軸 (時間軸)** | 固定幅スライディングウィンドウ。右端=「今」で毎フレーム進み、履歴は左へ平行移動するだけ（既描画点は組み変わらない）。幅は 1/2/5/10/30/60/120/300 秒から選択 | 10秒 |
| **Y軸 (値軸)** | ヒステリシス付き Auto-scale：クリップ時は即拡大、縮小はデータがレンジの60%未満を3秒継続したときのみ。レンジは1-2-5系の「キリのいい」値に量子化 | Auto |
| **無データ時** | ウィンドウは進み続け、右端の空白がストリーム停止を可視化する（プレースホルダには戻らない） | - |

正式な要求定義は `docs/21_system_requirements.md` SYS-F-5xx を参照。

### 表示データ量

| 設定 | 説明 | デフォルト |
|------|------|-----------|
| **表示ポイント数** | X軸上の最大ポイント数 | 500 |
| **スクロールウィンドウ** | 古いデータを押し出すスクロール幅 | 表示幅 |

### ビュー状態とズーム・パン

3つのビュー状態をフッターに常時表示する：

| 状態 | 表示 | 意味 |
|------|------|------|
| **LIVE** | `● LIVE`（緑） | 右端追従。デフォルト |
| **Inspect** | `🔍 Inspect`（青） | ズーム/ドラッグ操作で自動遷移。ビュー凍結、パン・ズームで過去範囲をスクロールバック取得。ヘッダーの `▶ LIVE` ボタンかダブルクリックで復帰 |
| **Paused** | `⏸ Paused` | Pause ボタン。ポーリング停止（バックエンドの収集は継続） |

| 操作 | 動作 |
|------|------|
| **マウスホイール** | Y軸ズーム（Inspect へ遷移） |
| **Shift + ホイール** | X軸ズーム（Inspect へ遷移） |
| **ドラッグ** | 範囲選択ズーム（Inspect へ遷移） |
| **ダブルクリック / ▶ LIVE** | LIVE（右端追従）へ復帰 |

### 間引き戦略 (Downsampling)

高速データ受信時の描画負荷軽減：

| 手法 | 説明 |
|------|------|
| **LTTB (Largest Triangle Three Buckets)** | 波形の特徴を維持したダウンサンプリング。各バケットから最も特徴的なポイントを選択 |
| **Average (平均 + Min/Max バンド)** | 各バケットの min/max を帯として描画し、中央線として平均値を表示 |

**モード切替:** データ受信中でも LTTB ↔ Average を即座に切替可能。内部で全統計値（min/max/avg）を保持するため、データの再構築は不要。

## ステートタイムライン (State Timeline)

### 基本機能

| 機能 | 説明 |
|------|------|
| **状態可視化** | 離散的な状態変化を水平バーで表示 |
| **複数チャンネル** | 各状態チャンネルを行として表示 |
| **色分け** | 状態ごとに異なる色を割り当て |
| **持続時間表示** | 各状態の継続時間をバーの長さで表現 |

### 状態の解釈

| データ型 | 状態解釈 |
|----------|----------|
| **文字列** | そのまま状態名として使用 |
| **数値（離散）** | 閾値設定で状態に変換 (例: 0=OFF, 1=ON) |
| **Boolean** | true/false を ON/OFF として表示 |

### 表示設定

| 項目 | 説明 | デフォルト |
|------|------|-----------|
| **行高さ** | 各チャンネルの行の高さ | 24px |
| **値表示** | バー内に状態名を表示 | ON |
| **色マッピング** | 状態 → 色 の対応設定 | 自動 |

### ウィンドウ構成 (Docking System)

## バックエンド実装

### データストア設計

```rust
/// プロッタ用のデータ集約ストア
/// メモリ制限付きでデータを保持し、表示時に動的集約を行う
pub struct PlotterAggregator {
    /// 3バッファ設計：
    /// - history: 確定済み履歴（AggregatedBucket形式）
    /// - buffer: 中間バッファ（AggregatedBucket形式）
    /// - raw_buffer: 未集約の生データ
    
    history: HashMap<String, Vec<AggregatedBucket>>,
    buffer: HashMap<String, Vec<AggregatedBucket>>,
    raw_buffer: HashMap<String, VecDeque<(u64, f64)>>,
    
    /// 現在の集約レベル（1 = 未圧縮、レベルアップごとに2倍）
    current_level: usize,
    
    /// ステート用データ（状態変化リスト）
    state_data: HashMap<String, Vec<StateChange>>,
    
    /// 設定
    config: PlotterConfig,
}

/// モード非依存の集約バケット
/// 全統計値を保持することで、表示時に LTTB/Average を即座に切替可能
#[derive(Debug, Clone)]
struct AggregatedBucket {
    ts: u64,      // タイムスタンプ（バケット内の先頭/末尾の平均）
    min: f64,     // 最小値
    max: f64,     // 最大値
    avg: f64,     // 平均値
    count: usize, // 生ポイント数（加重平均計算用）
}

impl AggregatedBucket {
    /// 集約モードに応じてAggregatedPointに変換
    fn to_point(&self, mode: &AggregationMode) -> AggregatedPoint {
        match mode {
            AggregationMode::Lttb => AggregatedPoint::Single {
                ts: self.ts,
                value: self.avg,  // LTTBは平均値を使用
            },
            AggregationMode::Average => AggregatedPoint::MinMax {
                ts: self.ts,
                min: self.min,
                max: self.max,
            },
        }
    }
}
```

**3バッファ設計のフロー:**
```text
1. 新データ → raw_buffer に追加

2. raw_buffer が bucket_size に達したら:
   ┌─────────────────────────────────────────┐
   │  raw_buffer から bucket_size 個を取出   │
   │  ↓                                      │
   │  AggregatedBucket に集約（min/max/avg）  │
   │  ↓                                      │
   │  buffer に追加                           │
   └─────────────────────────────────────────┘

3. history + buffer が max_points を超えたら:
   ┌─────────────────────────────────────────┐
   │  history + buffer を結合・再集約         │
   │  ↓                                      │
   │  新しい history として保存               │
   │  ↓                                      │
   │  current_level *= 2                      │
   └─────────────────────────────────────────┘
```

**設計の特徴:**
- **モード非依存ストレージ**: min/max/avg/count を全て保持
- **即座のモード切替**: `to_point(mode)` で表示時に変換
- **精度維持**: 加重平均で再集約時も精度を保持
- **バッチ処理対応**: 高速データ受信に対応（1000行/秒以上）

### 解析スレッド (Parser Thread)

*   **役割:** メインの `DataStore` から新しいデータを読み出し、行ごとにパースして `PlotterAggregator` に格納する。
*   **バッチ処理:** 全データを一括読み込み・一括追加でロック取得オーバーヘッドを最小化。
*   **負荷分散:** 受信スレッドとは独立して動作し、メインの通信を阻害しない。

### スマートポーリング (Version Counter)

フロントエンドの 60Hz ポーリングによる CPU オーバーヘッドを削減するため、軽量なバージョンチェック API を使用する。

```text
Frontend (60Hz)          Backend
    │                       │
    │── check_version() ──>│  (8 bytes)
    │<── {version, has_data}│
    │                       │
    │  version changed?     │
    │  └─ YES ─────────────>│── get_chart_data() ──>
    │                       │<── Full payload (KB~)
    │  └─ NO: skip          │
```

**API 仕様:**

```rust
/// Version info for lightweight polling
#[derive(Debug, Clone, serde::Serialize)]
pub struct PlotterVersionInfo {
    pub version: u64,
    pub has_data: bool,
}

/// Lightweight check: returns version and whether data exists
/// This is O(1) and doesn't require any data processing
pub fn check_version(&self) -> PlotterVersionInfo
```

**効果:**

| シナリオ | 変更前 | 変更後 |
|----------|--------|--------|
| アイドル時 | 60 heavy IPC/秒 | 60 light IPC/秒 |
| 10Hz データ | 60 heavy IPC/秒 | 10 heavy + 50 light IPC/秒 |
| 60Hz データ | 60 heavy IPC/秒 | 60 heavy IPC/秒（変化なし） |

データレート < 60Hz の場合、**70-80% の CPU 削減**が期待される。


### 動的集約 API

大量のデータを効率的に転送するため、表示範囲のみを抽出し動的に集約するAPIを提供する。
フロントエンドでのデータ変換を不要にするため、uPlot形式で直接返却する。

#### リクエスト構造

```rust
#[derive(Debug, Deserialize)]
pub struct PlotterDataRequest {
    /// 表示開始時刻（ms）、None = 全データの開始
    pub time_min_ms: Option<u64>,
    /// 表示終了時刻（ms）、None = リアルタイム追従
    pub time_max_ms: Option<u64>,
    /// 描画領域の幅（ピクセル）
    pub pixel_width: u32,
    /// リアルタイム追従モードか
    pub is_realtime: bool,
}
```

#### レスポンス構造（uPlot形式）

```rust
/// MinMaxバンドデータ（Averageモード用）
#[derive(Debug, Clone, Serialize)]
pub struct BandSeriesData {
    /// 最小値（タイムスタンプと同じインデックス）
    pub min: Vec<Option<f64>>,
    /// 最大値（タイムスタンプと同じインデックス）
    pub max: Vec<Option<f64>>,
}

/// uPlot形式のチャートペイロード
#[derive(Debug, Clone, Serialize)]
pub struct PlotterChartPayload {
    /// uPlot aligned data: [timestamps, ch0_values, ch1_values, ...]
    /// - aligned_data[0]: タイムスタンプ（秒、f64）
    /// - aligned_data[1..]: channel_names順の値
    /// Option<f64> は JSON null に直接シリアライズ
    pub aligned_data: Vec<Vec<Option<f64>>>,

    /// チャンネル名（aligned_data[1..]と対応）
    pub channel_names: Vec<String>,

    /// MinMaxバンドデータ（Averageモード時のみ）
    pub band_data: Option<HashMap<String, BandSeriesData>>,

    /// ステートタイムラインデータ
    pub state_data: HashMap<String, Vec<StateChange>>,

    /// チャンネルメタデータ（凡例用）
    pub channels: Vec<ChannelInfo>,

    /// 実際のデータ範囲（ms）
    pub start_ms: u64,
    pub end_ms: u64,
}
```

**設計ポイント:**
- `aligned_data` はuPlotがそのまま使用可能な形式
- `Option<f64>` は欠損データを表し、JSON `null` にシリアライズ
- フロントエンドでのデータ変換が不要（メモリリーク対策）
- `band_data` はAverageモード時のmin/max帯域描画用

#### 集約ロジック

| 条件 | 動作 |
|------|------|
| データ数 ≤ target_points × threshold | 集約なし（Single点として返却） |
| データ数 > target_points × threshold | バケット集約（Average/MinMax） |

- **target_points**: `min(pixel_width, 4000)` でキャップ
- **threshold**: デフォルト2（Average/MinMax）、10（LTTB）

#### キャッシュ管理

集約結果をキャッシュし、以下の条件で無効化：
- **リアルタイムモード**: 時間スパンが変化
- **フリーズモード**: 時間範囲が変化
- **共通**: ピクセル幅が20%以上変化

## フロントエンド実装

### 技術選定
*   **チャートライブラリ:** [uPlot](https://github.com/leeoniya/uPlot) - 圧倒的なパフォーマンスのため採用（インストール済み）。
*   **ステートタイムライン:** uPlotカスタムプラグインで実装。uPlotは時間軸・ズーム/パン・カーソル同期のみ担当し、状態バーはプラグインの`hooks.draw`でCanvas矩形描画。
*   **ウィンドウ管理:** Tauriのマルチウィンドウ機能を利用。

### データフロー（最適化後）

```text
Backend (Rust)                    Frontend (TypeScript)
┌──────────────────┐             ┌────────────────────────────────┐
│ PlotterAggregator│             │ PlotterWindow                  │
│                  │  IPC/Tauri  │   │                            │
│ get_chart_data() ├────────────►│   ▼ setData(payload)           │
│                  │             │   │                            │
│ PlotterChart     │             │   │ ← 変換不要！直接渡す       │
│ Payload          │             │   ▼                            │
│ (uPlot形式)      │             │ LineChart                      │
└──────────────────┘             │   │                            │
                                 │   ▼ uPlot.setData(alignedData) │
                                 │       └─ series.show で非表示  │
                                 └────────────────────────────────┘
```

**最適化ポイント:**
- バックエンドでuPlot形式に変換済み（`PlotterChartPayload`）
- フロントエンドでの毎フレーム変換処理が不要
- チャンネル非表示は `series.show` で制御（データフィルタリング不要）
- メモリリーク防止（毎フレームのオブジェクト生成なし）

### ステートタイムラインプラグイン設計

```typescript
// 状態セグメント（end_msは常に確定値、Noneは現在時刻に変換）
type StateSegment = { start_ms: number; end_ms: number; state: string };
type StateRow = { channel: string; segments: StateSegment[] };

// プラグイン設定
type StateTimelinePluginOpts = {
  getRows: () => StateRow[];           // 最新データ参照
  rowHeight: number;                   // 例: 24px
  stateColors: Record<string, string>; // 状態→色マッピング
  showLabel: boolean;                  // バー内テキスト表示
};
```

**プラグインの動作:**
1. uPlotの`hooks.draw`内でCanvasコンテキストを取得
2. 表示範囲内のセグメントのみ描画（`u.scales.x.min/max`でフィルタ）
3. `u.valToPos()`で時間→座標変換、矩形を`fillRect()`で描画
4. 状態の色はハッシュベースで自動割当（セッション内固定）

### ウィンドウ構成
*   メインウィンドウとは別の `WebviewWindow` として生成。
*   単一インスタンス設計（既存ウィンドウがある場合はフォーカス）。

### パフォーマンス最適化
*   **Rust側パース:** 文字列処理はすべてRustで行い、フロントエンドへは数値配列のみを渡す。
*   **時間範囲フィルタリング:** `get_plotter_data_ranged` で表示範囲のみ抽出・集約して返す。
*   **セグメント数制御:** 同一state連続はBackendでマージ済み。

## 変更履歴

### 2026-01-03: フロントエンドメモリリーク修正

#### 問題
リアルタイムプロット中にフロントエンドのメモリ使用量が急激に増加する問題が発生。

| 指標 | 測定値 |
|------|--------|
| 増加率 | +13.6 MB/秒 |
| 50秒後 | 90MB → 769MB (+680MB) |
| バックエンド | 安定 (~40MB) |

#### 根本原因
毎フレーム（60fps）で新規JavaScriptオブジェクトを大量生成していた：

1. **PlotterWindow.tsx** の `convertAggregatedData()`:
   - `HashMap`, `Array`, `Set` を毎フレーム新規作成
   - バックエンドから受信した `AggregatedPoint[]` を uPlot形式に変換

2. **LineChart.tsx** の `buildChartData()`:
   - `Set`, `Map`, `Array` を毎フレーム新規作成
   - タイムスタンプ統合、欠損値補完処理

#### 検討した解決策

| 案 | 概要 | 採否 |
|----|------|------|
| **A: バックエンド変換** | Rustでデータ変換、uPlot形式で返却 | ✅ 採用 |
| B: オブジェクトプール | フロントエンドで配列を再利用 | ❌ 不採用 |

**採用理由 (Option A):**
- Rust側での変換はメモリ効率が高い
- IPCオーバーヘッドはuPlot形式でも最小限
- フロントエンドのコードが大幅に簡素化
- `Option<f64>` → JSON `null` の直接シリアライズが可能

**不採用理由 (Option B):**
- GC問題の根本解決にならない
- コードの複雑性が増す
- uPlotの要求形式との整合性維持が困難

#### 実装内容

**バックエンド:**
- `PlotterChartPayload` 構造体追加（uPlot aligned data形式）
- `BandSeriesData` 構造体追加（min/maxバンド用）
- `get_chart_data()` メソッド実装
- `get_plotter_chart_data` Tauriコマンド追加

**フロントエンド:**
- `convertAggregatedData()` 関数削除
- `buildChartData()` 関数削除
- `alignedData` を直接uPlotに渡す
- `hiddenChannels` を `series.show` で制御

#### 結果

| 指標 | 修正前 | 修正後 |
|------|--------|--------|
| 60秒時点メモリ | ~860MB（継続増加） | ~210MB（安定） |
| 増加率 | +13.6 MB/秒 | 0 MB/秒 |
| 長時間稼働 | メモリ枯渇 | 問題なし |

### 2026-09-03: 総合バグ修正（マルチエージェントレビュー）

全サブシステムの並列コードレビュー＋敵対的検証により 58 件のバグを確定し、主要なものを修正。

#### プロッタが止まる・表示されない系（最重要）

| 修正 | 内容 |
|------|------|
| **DataStore 差し替え追従** | `open_port` / `clear_data` は DataStore を新インスタンスに差し替えるが、プロッタスレッドは起動時の `Arc<DataStore>` を掴んだままポーリングし続け、ポート再接続・クリア後にプロットが永久停止していた。スレッドは共有ハンドル（`Arc<Mutex<Option<Arc<DataStore>>>>`）から毎ポーリングで現在のストアを解決し、差し替え検知でオフセットとパーサをリセットする方式に変更。ポートを開く前にプロッタウィンドウを開いても動作するようになった |
| **temp ディレクトリ破壊** | 全 DataStore が同一の `%TEMP%/SerialMonitorEssential/<pid>` を共有し、旧インスタンスの Drop（プロッタスレッドの Arc 解放後に遅延実行）が新インスタンスのライブなデータファイルを削除していた。インスタンスごとに一意のサブディレクトリを使用 |
| **ウィンドウ X 閉じ** | X ボタンで閉じると React の unmount クリーンアップが走らず、スレッドと収集が永久に残っていた。`WindowEvent::Destroyed` でバックエンドが確実に停止 |
| **セパレータ固定** | 最初の行（起動バナー等）で区切り文字が固定され、以後の CSV が永久にパース不能だった。行ごとに再判定 |
| **Logger フラッシュ順序** | チャンクを finished_list から pop してから archived_index に登録していたため、その間データがどちらにも存在せず `get_data` が失敗（プロッタの読み取り停止・表示欠落の一因）。「書き込み→index 公開→pop」の順序に変更。I/O エラー時もデータが失われず再試行される |

#### 表示の正確性

| 修正 | 内容 |
|------|------|
| **タイムスタンプ潰れ** | 1 回のポーリングで読んだ全行に同一タイムスタンプが付き、表示時に同一 ts の点が上書きされ消えていた。バッチ内で時刻を分散配置（約 1ms/行、単調性維持） |
| **Average の中央線** | `(min+max)/2` を描画していた（仕様は加重平均）。`AggregatedPoint::MinMax` に `avg` フィールドを追加し真の平均を使用 |
| **クリア後の残像** | `has_data=false` だとフェッチをスキップし古いグラフが残っていた。バージョン変化時は常にフェッチ |
| **state のみのデータ** | 数値チャンネルが無いと「No data yet」でステートタイムラインに到達不能だった。x レンジのみのペイロードを返し、フロントも state のみで描画 |
| **DPI スケーリング** | ステートタイムラインが CSS px と Canvas デバイス px を混在させ、Windows の 125/150% 表示でバーが x 軸に重なっていた。devicePixelRatio でスケール |
| **チャート初期スケール** | チャート再生成時にスケール未設定で y が uPlot 既定の [-1000,1000] になっていた。生成直後にスケール設定＋ズーム状態リセット |
| **凡例の不整合** | uPlot 内蔵凡例のクリックが `hiddenChannels` 状態と不整合を起こすため内蔵凡例を無効化（カスタム凡例に一本化） |

#### 安定性・その他

- ヘッダー誤検出（数値データ受信後の非数値複数列行がヘッダー扱いされ全チャンネル名が変わる）→ 数値データ受信前のみ検出
- パーサの O(n²) バッファ複製 → バイトレベル 1 パスに書き換え。UTF-8 マルチバイト文字の読み取り境界分割破損も同時に解消。改行無しストリームでのバッファ無制限成長も 64KB でキャップ
- state_data の無制限成長 → 1 チャンネル 10,000 変化でキャップ（古い方から破棄）
- リアルタイムモードでの無意味なキャッシュ保存（毎フレーム全チャンネル分の deep copy）を省略
- `open_port` 失敗時に既存キャプチャが消える → 新ポートのオープン成功後に旧ストアを破棄
- 60Hz の `get_plotter_chart_data` / `check_plotter_version` を async 化（メインスレッドをブロックしない）
- シリアル送信の部分書き込み（`write` → `write_all`）
- ボーレート入力の検証（空欄/0/負数/小数を拒否、バックエンドにも 0 チェック）
- ASCII/Hex ビューアのフェッチ欠落（in-flight 中の強制リフェッチが破棄され最終データが表示されない）→ ペンディングキュー化、force フラグ保持
- 高速スクロール時の空白表示 → 表示オフセットをクランプ
- 不正 HEX（"4G" 等）の誤送信 → 厳密検証
- Ctrl+A 警告が Send テキストエリア等の select-all を奪う → 編集要素では無効
- 送信履歴の ↑↓ がマルチライン編集のカーソル移動を奪う → 先頭/末尾行のみ反応、下書きの退避/復元
- Tauri イベントリスナーの二重登録（StrictMode/HMR）、ポートリスト更新の stale closure、Auto Scroll ON 時の即ジャンプ、ビューアのリサイズ追従、タイムスタンプ index の単調性保証、poisoned lock での panic 回避 など

#### 挙動変更

- **Clear / ポート再接続時、プロッタのデータもクリアされる**ようになった（DataStore 差し替えをプロッタスレッドが検知した時点で集約器をリセット）。メインビューが空になるのにプロッタだけ旧セッションのチャンネルが混在し続ける不整合を解消。
- **メインウィンドウを閉じるとプロッタウィンドウも閉じ、アプリが終了する**ようになった（従来はプロッタが開いたままだとプロセスが残り続けた）。
- **ASCII ビューアの Timestamp トグルが即座に表示へ反映される**ようになった（従来はスクロールか新データ到着まで古い表示が残った）。

#### 検証

- Rust 114 テスト（回帰テスト追加: ストア差し替え追従＋クリア、タイムスタンプ分散、セパレータ再判定）/ フロントエンド 79 テスト全パス
- clippy / tsc / eslint / プロダクションビルド クリーン
- 修正 diff 自体への敵対的レビュー（別ワークフロー）でリグレッション 12 件を検出・修正
- **com0com 仮想 COM ペア（COM15⇔COM16）での E2E 試験**（UIA による UI 自動操作＋スクリーンショット検証）:
  - ラベル付きデータ `time:x,sin:x,cos:x,random:x,motor:ON,pump:OFF` のライン4ch＋state 2ch 同時描画
  - state のみのストリーム（テキスト行）でステートタイムライン表示（旧: No data yet のまま）
  - Clear 後にプロットがリセットされ継続更新（旧: 永久フリーズ）
  - 切断→再接続後にプロットがリセットされ継続更新（旧: 永久フリーズ）
  - プロッタを先に開いてからポート接続してもデータが流れる（旧: 動かない）
  - ウィンドウ X 閉じでバックエンドのスレッド停止・収集停止（旧: 永久残留）
  - temp ディレクトリがインスタンス単位（`<pid>/<n>`）で安全に削除されることをログで確認
- **モード切替の総当たり E2E**（ストリーミング中および停止中の任意タイミング操作）:
  - Downsample LTTB↔Average（ストリーミング中・一時停止中の両方、Average の min/max バンド描画確認）
  - Pause↔Resume、凡例クリックによるチャンネル表示/非表示（Y 軸再スケール確認）
  - Hex↔ASCII 切替、Line Wrap / Timestamp / Auto Scroll / DTR / RTS トグル
  - 複合連続操作（Clear×3＋Pause/Resume＋モード切替×2＋切断/再接続の連打）後も正常回復
  - メインウィンドウ閉→プロッタ連動クローズ→プロセス終了（exit 0）、vite ポート 1420 も解放

#### 既知の未修正（低優先）

- 検索ボックス / Filter トグルが未実装（UI のみ存在）
- min/max バンドが線の上に描画され y オートスケールにも含まれない（視覚上の軽微な問題）
- 一時停止中の手動スクロールとアンカー再計算が競合し得る（100ms スロットル分のラグ）

### 2026-09-03 (2): ライブ表示のスライディングウィンドウ化

「最新データを受けてプロットがバタバタする」問題を、ユーザー意図（①今を見る ②事件を見つける ③後から調べる）から仕様を再定義して解消。詳細な要求は `docs/20_user_needs.md` / `docs/21_system_requirements.md`、設計判断は `docs/22_architecture_description.md` ADR-06〜08 を参照。

#### 変更内容

| 層 | 変更 |
|----|------|
| バックエンド | リアルタイム要求の集約を**絶対時刻整列・1-2-5系量子化幅のバケット**に変更。確定セルは以後のフェッチでバイト単位に同一（ウィンドウがスライドしても過去の波形が組み変わらない）。LTTB は静的範囲（Inspect）専用に |
| フロントエンド | 固定幅スライディングウィンドウ（デフォルト10s、フッターで選択）。右端は rAF ごとにローカルで前進し `setScale` のみ（IPC なし）、データ取得は従来どおり version 変化時のみ。LIVE/Inspect/Paused の3状態モデル、Inspect でのスクロールバック取得、Yヒステリシス（即拡大・3秒60%未満で縮小・1-2-5量子化） |

#### バタバタの原因（修正前）

1. X軸が全履歴表示で毎フレーム伸縮
2. Y軸が毎フレーム min/max±10% 再計算
3. LTTB・バケット境界が「現在の時間範囲」基準で毎フレーム再計算され、**過去の波形の形まで組み変わる**

#### 検証

- バックエンド: 整列バケットの安定性を例示テスト＋プロパティテスト（`prop_aligned_realtime_stability`）で検証。計 126 テスト
- フロントエンド: 93 テスト（ウィンドウ選択・明示レンジ要求・LIVE/Inspect遷移・空ウィンドウ維持・Clear リセット等 14 件追加）
- E2E（com0com + UIA）: 10s/30s ウィンドウ幅、ホイール→Inspect→▶LIVE 復帰、ストリーム停止時のスクロール継続（空白の可視化）、Clear→プレースホルダ復帰を実機確認
- ペアワイズ E2E: 8因子・112ペアを7行で網羅、全行 PASS（ハーネスは `test_tools/e2e/` に永続化）
