# システム要求仕様 (System Requirements Specification)

## 目的

[20_user_needs.md](20_user_needs.md) のステークホルダーニーズを、**検証可能な要求**へ変換したもの。
ISO/IEC/IEEE 29148 の要求記述スタイル（一意な ID、shall 形式、根拠、検証方法）に倣うが、
1人開発で維持できる分量に絞る。

## スコープ

本書は「システムが何を満たすか」を定める。**どう実現するか**は [22_architecture_description.md](22_architecture_description.md) に置く。
ただし、ニーズの側から見て実現方式そのものが要求である場合（例: ライブ表示の定常性）は、
観測可能な性質として本書に書く。

## 記法

| 項目 | 規約 |
|------|------|
| **ID** | `SYS-F-<百番台><連番>` = 機能要求、`SYS-NF-<百番台><連番>` = 品質要求。百番台はサブシステム／品質特性ごとに固定。**欠番は詰めない**（後からの挿入で番号が崩れないよう、連番は 10 刻みではなく末尾追加とする） |
| **shall** | 日本語では「〜すること」で表す。「〜してもよい」(may) / 「〜が望ましい」(should) は明示的にそう書く |
| **上流** | 由来するニーズ ID。複数可 |
| **検証** | **T**=Test（自動テスト）、**I**=Inspection（コード／文書レビュー）、**A**=Analysis（解析・計算）、**D**=Demonstration（実機／E2E 実演） |
| **状態** | 実装済 = 現行コードで満たす／部分 = 一部のみ／**計画** = 本書で定義したが未実装（[23_traceability.md](23_traceability.md) の GAP に対応） |

# A. 機能要求 (SYS-F)

## A.1 シリアル接続 (1xx)

| ID | 要求 | 根拠 | 上流 | 検証 | 状態 |
|----|------|------|------|------|------|
| **SYS-F-101** | システムは、利用可能なシリアルポートを列挙し、USB / PCI / Bluetooth の種別に応じた識別名（例: `Pico (COM15)`）で提示すること | 複数ポートがある環境で目的のデバイスを選び間違えないため | UN-20 | T, D | 実装済 |
| **SYS-F-102** | システムは、ボーレート、データビット (5/6/7/8)、パリティ (None/Odd/Even)、ストップビット (1/2)、フロー制御 (None/Software/Hardware) を指定してポートを開けること | デバイス側の設定に合わせられなければ通信が成立しない | UN-20 | T, D | 実装済 |
| **SYS-F-103** | システムは、9600 から 12 Mbps までの非標準を含むボーレートを、OS とドライバが許容する範囲で受け付けること | FPGA・高速センサでは 12 Mbps 級が実用域（[01_overview.md](01_overview.md)） | UN-15 | D | 実装済 |
| **SYS-F-104** | システムは、ポートを開いた直後に DTR / RTS を設定値どおりに駆動すること。また接続中の DTR / RTS 変更を即座に反映すること | Arduino 系デバイスは DTR/RTS がアサートされないと送信を開始しない | UN-09 | I, D | 実装済 |
| **SYS-F-105** | システムは、不正な設定値（ボーレート 0、空欄、負数、小数、未知のパリティ名等）を**ポートを開く前に**拒否し、エラー理由を利用者に示すこと | 不正値で開くと、症状が「無反応」になり原因追跡が困難になる | UN-17 | T, D | 実装済 |
| **SYS-F-106** | システムは、ポートのオープンに失敗した場合、**直前のセッションの受信データを破棄しないこと** | 「別ポートを開こうとして失敗したら今までのログが消えた」は回復不能な損失 | UN-10, UN-17 | I, D | 実装済 |
| **SYS-F-107** | システムは、受信中に致命的な I/O エラー（デバイス切断等）を検知した場合、受信を停止し、フロントエンドへ切断を通知すること。**加えて、2 秒間隔でポート一覧を能動的に再列挙し、着脱を一覧へ反映すること**。ただし接続中は、再列挙によって選択中のポートが利用者に無断で変更されないこと | 来ないデータを待ち続けさせないため。挿し直したデバイスがアプリの再起動なしに現れないと、実機デバッグの往復ごとに再起動が必要になる | UN-19 | T, D | 実装済（*1） |
| **SYS-F-108** | システムは、フレーミングエラー・パリティエラー等の**非致命的な受信エラーでは受信を継続すること** | ノイズ 1 バイトでセッションが落ちるとログ取得が成立しない | UN-10 | I | 実装済 |
| **SYS-F-109** | システムは、同一 COM ポートを再オープンする際、先に旧セッションの受信を停止して OS ハンドルを解放してから開くこと | ハンドルが残っていると排他アクセスエラーで再接続に失敗する | UN-12, UN-17 | I, D | 実装済 |

> (*1) **2026-09-03 実装（GAP-07 / GAP-08 解消）**。責務を 2 つに分ける。
> **切断の権威は read エラー経路**（`worker_thread.rs` → `serial-status`）にあり、ここは変更していない。
> 能動検知は `src/App.tsx` の `PORT_POLL_INTERVAL_MS = 2000` によるポート一覧の再列挙で、
> **一覧の更新のみ**を行う（接続中に選択が黙って移動しないことをテストで固定）。
> OS のデバイス着脱通知（Windows の `WM_DEVICECHANGE`）は使わない — プラットフォーム固有 API の
> 直接呼び出しを避ける方針（SYS-NF-501）と、2 秒の遅延が UN-19 の要求に対して十分小さいため。
> また `serial-status(connected=false)` の受信時にフロントエンドが `close_port` を呼び、
> バックエンドのポートハンドルを解放して UI 状態と再同期する（旧 GAP-08 / DEBT-1）。

## A.2 受信・保存 (2xx)

| ID | 要求 | 根拠 | 上流 | 検証 | 状態 |
|----|------|------|------|------|------|
| **SYS-F-201** | システムは、受信した全バイトを、受信順・欠落なしで保持すること。UI の描画遅延が受信の停止・欠落を引き起こさないこと | ツールとしての存在意義（[01_overview.md](01_overview.md) データ完全性） | UN-10, UN-15 | T, A, D | 実装済 |

| **SYS-F-203** | システムは、任意のバイト範囲 `(offset, length)` の読み出し要求に対し、ディスク上の確定データとメモリ上の未確定データを**継ぎ目なく**結合して返すこと | 表示要求は 2 つの記憶域の境界をまたぐ。境界で欠落すると表示が飛ぶ | UN-07, UN-10 | T | 実装済 |
| **SYS-F-204** | システムは、いかなる時点でも、受信済みのバイトが**ディスクとメモリのどちらにも存在しない瞬間を作らないこと** | 2026-09-03 修正前は pop → 書き込みの順序でこの瞬間があり、読み出し失敗とプロット欠落を招いた | UN-10, UN-17 | T, I | 実装済 |
| **SYS-F-205** | システムは、ディスク書き込みに失敗した場合でも該当データを失わず、再試行の対象として保持し続けること。またディスクフル等のエラーを利用者に通知すること。通知は同種のエラーが連続しても 5 秒に 1 回までに抑えること | 書き込み失敗でデータが消えるのは SYS-F-201 違反。ディスクフルは毎周期発生するため、抑制しないと通知が画面を埋める | UN-10 | T, I | 実装済（*2） |
| **SYS-F-206** | システムは、受信バイト総数の変化をフロントエンドへ通知すること。通知頻度は約 60 通知/秒（16 ms 間隔）を上限に間引くこと | 12 Mbps では 1 バイトごとの通知は不可能。UI 側の更新契機だけが必要 | UN-15 | I, D | 実装済 |
| **SYS-F-207** | システムは、受信データに対して約 100 ms 間隔で受信時刻を記録し、任意のバイトオフセットに対応する時刻を取得できること | ASCII ビューアのタイムスタンプ列。全バイトに時刻を持たせるのは容量的に不可 | UN-07 | T | 実装済 |
| **SYS-F-208** | システムは、受信データ中の改行 (LF) 位置を受信時に索引化し、行番号からバイト範囲を取得できること | 行指向の ASCII 表示で、表示のたびに全走査しないため | UN-07 | T | 実装済 |
| **SYS-F-209** | システムは、一時ファイルをシステムの一時ディレクトリ配下に置き、**インスタンスごとに一意な**サブディレクトリを用いること。アプリ終了時に自分の領域を削除し、起動時に使用されていない過去の領域を削除すること | 利用者のディスクを汚さない。かつ、同一プロセス内の旧インスタンスの後始末が新インスタンスのライブデータを消さないため（2026-09-03 修正） | UN-14, UN-17, UN-21 | I, D | 実装済 |
| **SYS-F-210** | システムは、受信済みの全データをバイナリのままファイルへエクスポートできること。エクスポート中もメモリ使用量が受信データ量に比例して増加しないこと | 外部ツールでの解析。GB 級のログを一度にメモリへ載せない | UN-13, UN-16 | I, D | 実装済 |
| **SYS-F-211** | システムは、受信済みデータを Hex 文字列または ASCII 文字列としてクリップボードへ渡せること。大量データの場合は事前に利用者へ確認すること | 貼り付けて共有する運用。無警告のフリーズを避ける | UN-07 | I, D | 実装済 |

> (*2) チャンク単位で「書き込み → 索引公開 → 除去」の順序を守るため I/O エラー時のデータ損失は起きない。
> **2026-09-03 実装（GAP-09 解消）**: Logger スレッドに `on_error` コールバック（5 秒レート制限）を設け、
> `data_store.rs` がそれを `log-error` イベントとして emit、`src/App.tsx` が利用者へ提示する。
